# StackMedic Fix Notes: INC-0003

**Fix Type:** CODE
**Service:** BackgroundWorker
**Severity:** LOW

## Root Cause
The primary root cause is a race condition and lack of transactional integrity within the inventory management system's stock update logic. When multiple background processes attempt to decrement the stock count for PROD-005 concurrently, or when a fulfillment transaction fails after partially updating the stock (e.g., deducting from an in-memory counter but failing before committing the final database state), the system allows negative inventory counts. The logs indicate that the 'warehouse delta may be stale' and the 'stock commit not finalized,' confirming that concurrent updates are overwriting or bypassing necessary transactional locks, leading to data inconsistency.

## Recommended Fix
Modify the service method responsible for decrementing stock (e.g., `InventoryService.reserveStock(productId, quantity)`). This fix must implement proper database-level locking to ensure atomicity during inventory checks and updates. Specifically, use a mechanism like `SELECT FOR UPDATE` in SQL or utilize an appropriate transactional isolation level (e.g., SERIALIZABLE) within the application code to prevent concurrent transactions from reading stale stock levels or committing partial updates.

## Reason
The observed errors are classic symptoms of concurrency issues in a critical resource (inventory). Simply fixing model classes like Order.java will not resolve this; the fix must be applied to the service/repository layer that handles the actual stock write operations, ensuring that all reads and writes related to inventory changes occur within a single, isolated transaction boundary.
