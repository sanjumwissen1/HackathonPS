# StackMedic Fix Notes: INC-0003

**Fix Type:** CODE
**Service:** BackgroundWorker
**Severity:** CRITICAL

## Root Cause
The root cause is a transactional integrity failure (race condition or missing transaction boundary) between the inventory reservation service and the payment processing service. The system allows the payment acceptance process to proceed for an order when the order's state has not been fully finalized, specifically because the 'stock commit' (the finalization of reserved inventory) has not successfully completed. This results in orders being marked as having accepted payments while simultaneously lacking confirmed inventory reservations or proper transactional status updates.

## Recommended Fix
Modify the payment acceptance logic within the BackgroundWorker service (or the associated Order/Payment transaction handler). The core change must enforce that the payment gateway call can only be executed if a preceding, atomic step confirms both: 1) Inventory reservation is successful and finalized (`stock commit` completed); AND 2) The order state explicitly permits payment processing. Implement a robust retry mechanism with exponential backoff for transient inventory service failures to ensure eventual consistency before committing the payment.

## Reason
The current logic is non-atomic, allowing partial commits (payment recorded without finalized stock commit). By enforcing that the successful completion of the stock commit must be a prerequisite and part of the same transaction boundary as the payment acceptance, we ensure data integrity and prevent future `UNEXPECTED_PAYMENT_STATE` errors.
